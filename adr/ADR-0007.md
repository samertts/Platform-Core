# ADR-0007: Identity & Authentication

**Document**: Architecture Decision Record

**Status**: Accepted
**Deciders**: Platform Architect, Core Engineering Team, Security Team
**Constitution Reference**: Articles I, V, IX, XVII

## 1. Context

The Unified Healthcare Platform requires identity and authentication mechanisms that work across diverse deployment scenarios—from isolated government laboratories with no network connectivity to national-scale cloud deployments. The platform must support government-grade security requirements while maintaining usability for laboratory personnel.

**Platform Security Requirements**:
- JWT-based authentication for API access
- API key authentication for service-to-service
- OAuth2 for external integrations
- RBAC with roles: Platform Architect, Team Lead, Developer, Viewer
- Resource-level permissions for registry operations
- Policy-based access control for governance operations
- Encryption at rest and in transit
- No hardcoded secrets

**Iraqi Government Security Requirements**:
- Government-grade security standards
- Data sovereignty controls
- Audit trail requirements (7-year retention)
- Compliance with national security regulations
- Air-gapped deployment support

**Offline Constraint**: Authentication must work without network connectivity in government laboratories.

---

## 2. Problem

The identity and authentication system must satisfy:

**Requirement 1 - Offline Authentication**: Government laboratories must authenticate users without network connectivity. Local credential verification required.

**Requirement 2 - Government-Grade Security**: Iraqi government regulations require strong security controls, audit trails, and compliance reporting.

**Requirement 3 - Role-Based Access Control**: Different user roles require different permissions. Fine-grained access control for platform resources.

**Requirement 4 - Multi-Factor Authentication**: Critical operations may require additional verification steps.

**Requirement 5 - Session Management**: Secure session handling with appropriate timeout and refresh mechanisms.

**Requirement 6 - Audit Logging**: All authentication events must be logged for compliance and security monitoring.

**Requirement 7 - Credential Management**: Secure password storage, rotation, and recovery procedures.

**Requirement 8 - Integration**: Authentication must integrate with existing government identity systems where available.

---

## 3. Alternatives Considered

### Alternative A: Session-Based Authentication

**Description**: Traditional server-side sessions with cookies.

**Pros**:
- Simple implementation
- Server-side control
- Easy revocation
- No token storage issues

**Cons**:
- Requires server-side session storage
- Not suitable for distributed systems
- Scalability limitations
- Not offline-capable
- CSRF vulnerabilities

**Assessment**: REJECTED — Server dependency violates offline-first requirement.

### Alternative B: OAuth2/OIDC with External Provider

**Description**: Delegate authentication to external identity provider (Keycloak, Auth0, Azure AD).

**Pros**:
- Standardized protocol
- Federation capabilities
- Multi-factor support
- Professional security maintenance
- Integration with existing systems

**Cons**:
- Requires network connectivity
- External dependency for authentication
- Not offline-capable
- Government approval may be required
- Additional infrastructure

**Assessment**: REJECTED — Network dependency violates offline-first requirement.

### Alternative C: JWT-Based with RBAC and Offline Capability

**Description**: JWT tokens for authentication with RBAC for authorization and local credential verification for offline mode.

**Pros**:
- Stateless tokens (no server-side storage)
- Offline-capable with local verification
- Standardized format
- Scalable
- Fine-grained permissions via claims

**Cons**:
- Token revocation complexity
- Token size overhead
- Key management requirements
- Offline credential freshness concerns

**Assessment**: SELECTED — Best balance of security, scalability, and offline capability.

### Alternative D: Certificate-Based Authentication

**Description**: X.509 certificates for device and user authentication.

**Pros**:
- Strong cryptographic security
- No shared secrets
- Government-approved standard
- Offline-capable

**Cons**:
- Complex certificate management
- PKI infrastructure required
- User experience challenges
- Revocation complexity

**Assessment**: REJECTED — Complexity and user experience issues outweigh security benefits for user authentication.

---

## 4. Decision

**We will adopt JWT-based authentication with RBAC and offline-capable credential verification.**

### 4.2 JWT Token Structure

**Access Token**:
```json
{
    "header": {
        "alg": "RS256",
        "typ": "JWT",
        "kid": "key-id-123"
    },
    "payload": {
        "sub": "user-123",
        "iss": "platform-core",
        "aud": "platform-api",
        "exp": 1719340800,
        "iat": 1719337200,
        "jti": "token-123",
        "roles": ["developer", "viewer"],
        "permissions": ["repository:read", "repository:write"],
        "scope": "platform:full"
    }
}
```

**Refresh Token**:
```json
{
    "header": {
```

### 4.3 Role-Based Access Control (RBAC)

**Roles**:
| Role | Description | Permissions |
|------|-------------|-------------|
| Platform Architect | Full platform access | All permissions |
| Team Lead | Team management and oversight | Repository management, team operations |
| Developer | Development operations | Repository read/write, API access |
| Viewer | Read-only access | Repository read, API read |

**Permissions**:
| Resource | Read | Write | Delete | Admin |
|----------|------|-------|--------|-------|
| Repository | ✓ | ✓ | ✗ | ✗ |
| Service | ✓ | ✓ | ✗ | ✗ |
| API | ✓ | ✓ | ✗ | ✗ |
| Event | ✓ | ✓ | ✗ | ✗ |
| Device | ✓ | ✓ | ✗ | ✗ |
| Governance | ✓ | ✓ | ✗ | ✗ |
| Platform | ✓ | ✗ | ✗ | ✗ |

**Policy-Based Access Control**:
- Resource-level permissions for registry operations
- Policy-based access control for governance operations
- Time-based restrictions for sensitive operations
- Location-based restrictions for data sovereignty

### 4.4 Offline Authentication

**Local Credential Storage**:
- Bcrypt-hashed passwords stored locally
- Salted password hashes (cost factor 12)
- Offline credential cache with TTL
- Encrypted credential storage

**Offline Verification Process**:
1. User provides credentials
2. System loads cached credentials from local storage
3. Password hash verified against local cache
4. JWT token issued with offline claim
5. Token valid for limited duration (24 hours)
6. Audit log updated locally

**Synchronization**:
- Online authentication preferred when available
- Offline tokens synchronized when connectivity restored
- Conflict detection for credential changes
- Priority-based synchronization for security updates

### 4.5 Multi-Factor Authentication (MFA)

**MFA Methods**:
- TOTP (Time-based One-Time Password)
- SMS verification (when available)
- Hardware token (government-issued)
- Biometric (future enhancement)

**MFA Enforcement**:
- Required for Platform Architect role
- Required for governance operations
- Required for critical data modifications
- Configurable per organization

### 4.6 Session Management

**Session Structure**:
```python
@dataclass
class Session:
    session_id: str
    user_id: str
    created_at: datetime
    expires_at: datetime
    last_activity: datetime
    ip_address: str
    user_agent: str
    mfa_verified: bool
    offline: bool
```

**Session Policies**:
- Access token expiry: 1 hour
- Refresh token expiry: 30 days
- Idle timeout: 30 minutes
- Absolute timeout: 24 hours
- Maximum concurrent sessions: 5

### 4.7 Key Management

**Key Types**:
- RSA key pairs for JWT signing
- AES keys for encryption
- HMAC keys for checksums

**Key Storage**:
- Government-approved HSM for production
- Encrypted file storage for development
- Key rotation every 90 days
- Key escrow for disaster recovery

**Key Distribution**:
- Public keys distributed via JWKS endpoint
- Private keys secured in HSM
- Key versioning for rotation
- Key revocation capability

### 4.8 Audit Logging

**Authentication Events**:
- Login attempts (success/failure)
- Logout events
- Token refresh events
- MFA verification events
- Password changes
- Role changes

**Audit Log Structure**:
```json
{
    "event_id": "audit-123",
    "timestamp": "2026-06-25T10:00:00Z",
    "event_type": "login_success",
    "user_id": "user-123",
    "ip_address": "192.168.1.100",
    "user_agent": "Mozilla/5.0",
    "details": {
        "method": "password",
        "mfa_used": true
    }
}
```

**Retention**:
- Authentication logs: 7 years (government requirement)
- Security events: 10 years
- Audit logs: Immutable and tamper-evident

## 5. Consequences

### 5.1 Positive Consequences

**Security Benefits**:
- Government-grade security via JWT and RBAC
- Offline authentication for government laboratories
- Multi-factor authentication for critical operations
- Comprehensive audit logging

**Operational Benefits**:
- Stateless tokens reduce server load
- Offline capability enables field operations
- Scalable authentication for national deployment
- Integration with existing identity systems

**Compliance Benefits**:
- Constitution Article I (platform principles) satisfied
- Constitution Article V (shared services) satisfied
- Government security requirements met
- Audit trail for compliance reporting

### 5.2 Negative Consequences

**Complexity Costs**:
- JWT implementation requires careful security
- Offline credential management adds complexity
- Key management requires HSM infrastructure
- MFA adds user friction

**Operational Costs**:
- Key rotation requires coordination
- Offline credential synchronization adds overhead
- Audit log storage grows over time
- MFA enrollment requires user training

**Performance Costs**:
- JWT verification adds latency
- Offline verification may be slower
- Audit logging impacts performance
- MFA adds authentication time

---

## 6. Trade-offs

### 6.1 Security vs. Usability

**Trade-off**: Strong security measures add friction for users.

**Rationale**: Government healthcare data requires strong security. Usability improvements via intuitive interfaces and clear documentation.

**Mitigation**: Single sign-on where possible. Remember-me functionality. Clear security training. Usability testing.

### 6.2 Offline vs. Freshness

**Trade-off**: Offline credentials may be stale.

**Rationale**: Government laboratories require offline operation. Credential freshness maintained via synchronization when online.

**Mitigation**: Limited offline token validity (24 hours). Priority synchronization for security updates. Manual override capabilities.

### 6.3 Statefulness vs. Scalability

**Trade-off**: Session management adds state but improves security.

**Rationale**: JWT tokens provide scalability. Session management enables revocation and monitoring.

**Mitigation**: Short-lived tokens reduce revocation needs. Local session caching. Distributed session store for cloud deployments.

## 7. Risks

### 7.1 Technical Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| JWT token compromise | Medium | High | Short expiry, refresh rotation, revocation |
| Offline credential theft | Medium | High | Local encryption, secure storage, monitoring |
| Key management failures | Low | High | HSM, key escrow, recovery procedures |
| MFA bypass attempts | Low | High | Server-side validation, rate limiting |

### 7.2 Operational Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| User lockout from MFA | Medium | Medium | Recovery codes, admin reset procedures |
| Key rotation failures | Low | High | Automated rotation, fallback procedures |
| Audit log corruption | Low | High | Redundant storage, integrity checks |
| Session hijacking | Low | High | HTTPS, session binding, monitoring |

### 7.3 Compliance Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| Government audit failures | Low | High | Compliance documentation, regular audits |
| Data sovereignty violations | Low | High | Data residency controls, encryption |
| Authentication bypass | Low | High | Security testing, penetration testing |
