# ADR-0003: Database Strategy

**Document**: Architecture Decision Record
**ID**: ADR-0003
**Date**: 2026-06-25
**Status**: Accepted
**Deciders**: Platform Architect, Core Engineering Team
**Constitution Reference**: Articles II, III, V, XVII

---

## 1. Context

The Unified Healthcare Platform requires a database strategy that supports diverse deployment scenarios—from isolated government laboratories with no network connectivity to national-scale cloud deployments. Each repository must maintain its own data storage (Constitution Article III), and no shared databases are permitted between modules (Constitution Article XVII).

Platform-Core manages nine centralized registries:
1. Repository Registry
2. Service Registry
3. API Registry
4. Event Registry
5. Device Registry
6. Workflow Registry
7. Policy Registry
8. Plugin Registry
9. Knowledge Registry

Additionally, the Knowledge Graph requires graph storage capabilities for entity relationships and traversal queries. The platform must support:

- **Offline Mode**: Single-laboratory deployment with no network
- **Laboratory Mode**: LAN-based multi-user deployment
- **Cloud Mode**: National-scale deployment with full infrastructure

**Iraqi Infrastructure Constraints**:
- Government laboratories may have legacy systems with limited resources
- Network connectivity may be intermittent or unavailable
- Data must remain within national boundaries for sovereignty
- Backup and recovery must work in constrained environments
- Security requirements mandate encryption at rest and in transit

---

## 2. Problem

The database strategy must satisfy these competing requirements:

**Requirement 1 - Offline-First Operation**: The platform must function fully without network connectivity. Government laboratories must store and query data locally.

**Requirement 2 - Module Independence**: Each module maintains its own database (Constitution Article III). No shared databases between modules.

**Requirement 3 - Data Sovereignty**: Iraqi government regulations may require data to remain within national boundaries. Cloud deployments must support data residency controls.

**Requirement 4 - Scalability**: The platform must scale from single-laboratory SQLite to national-scale PostgreSQL without architectural changes.

**Requirement 5 - ACID Compliance**: Healthcare data integrity requires ACID transactions for critical operations (patient records, laboratory results).

**Requirement 6 - Graph Relationships**: The Knowledge Graph requires efficient traversal of entity relationships (repositories → services → APIs → events → devices).

**Requirement 7 - Performance**: Database operations must meet performance targets (<50ms p50 for API responses).

**Requirement 8 - Backup and Recovery**: All deployment modes must support reliable backup and recovery procedures.

---

## 3. Alternatives Considered

### Alternative A: SQLite for All Deployments

**Description**: Use SQLite as the sole database for all deployment modes.

**Pros**:
- Zero configuration and deployment
- Full ACID compliance
- Excellent performance for single-user operations
- Embedded database (no separate process)
- Government-friendly (no external dependencies)
- Strong data integrity guarantees

**Cons**:
- Limited concurrency (single-writer)
- No network access for multi-user scenarios
- Limited scalability for national deployment
- No built-in replication
- Memory limitations for large datasets

**Assessment**: REJECTED — Cannot support multi-user laboratory or national-scale deployments.

### Alternative B: PostgreSQL for All Deployments

**Description**: Use PostgreSQL as the sole database for all deployment modes.

**Pros**:
- Full ACID compliance
- Excellent concurrency and performance
- Advanced features (replication, partitioning, extensions)
- Strong ecosystem and tooling
- Government-grade security features
- Apache AGE extension for graph queries

**Cons**:
- Requires separate server process
- Complex deployment for offline environments
- Resource requirements too high for constrained devices
- Network dependency for client connections
- Configuration complexity for simple deployments

**Assessment**: REJECTED — Resource requirements and deployment complexity incompatible with offline-first requirement.

### Alternative C: SQLite for Edge, PostgreSQL for Server

**Description**: Use SQLite for offline/edge deployments and PostgreSQL for server/cloud deployments, with synchronization between them.

**Pros**:
- SQLite provides zero-configuration offline capability
- PostgreSQL provides scalability for cloud deployments
- Clear separation of deployment modes
- Synchronization enables eventual consistency
- Both databases support ACID compliance
- Apache AGE extension available for PostgreSQL graph queries

**Cons**:
- Two database technologies increase operational complexity
- Synchronization requires conflict resolution
- Data format differences may require transformation
- Testing matrix increased (two databases)
- Backup and recovery procedures differ

**Assessment**: SELECTED — Best balance of offline capability and scalability. Synchronization complexity manageable with proper design.

### Alternative D: Document Database (MongoDB)

**Description**: Use MongoDB for flexible document storage across all deployments.

**Pros**:
- Schema flexibility for evolving data models
- Good horizontal scalability
- Rich query language
- Built-in replication
- Strong JSON support

**Cons**:
- Limited ACID compliance (multi-document transactions)
- No foreign key constraints
- Government security concerns (NoSQL injection)
- Less mature healthcare ecosystem
- Memory requirements higher than SQLite
- Not suitable for offline-first with limited resources

**Assessment**: REJECTED — ACID limitations and security concerns incompatible with healthcare requirements.

### Alternative E: Graph Database (Neo4j)

**Description**: Use Neo4j for all data storage, including graph relationships.

**Pros**:
- Excellent graph traversal performance
- Cypher query language for complex relationships
- ACID compliance
- Built-in visualization tools
- Strong relationship modeling

**Cons**:
- Resource requirements too high for offline deployment
- Single-database approach violates module independence
- Licensing costs for enterprise features
- Government approval may be limited
- Not suitable for relational data (registries)

**Assessment**: REJECTED — Resource requirements and single-database approach incompatible with requirements.

## 4. Decision

**We will adopt SQLite for offline/edge deployments and PostgreSQL for server/cloud deployments, with no shared databases between modules.**

### 4.1 Database Selection by Deployment Mode

**Mode 1 - Standalone (Offline)**:
- **Primary Database**: SQLite 3.x
- **Location**: Local filesystem (`data/platform.db`)
- **Features**: Full ACID, WAL mode, JSON support
- **Limitations**: Single-writer, limited concurrency
- **Use Case**: Single-laboratory, disconnected operations

**Mode 2 - Laboratory (LAN)**:
- **Primary Database**: PostgreSQL 16
- **Location**: Local server or Docker container
- **Features**: Full ACID, replication, extensions
- **Advantages**: Multi-user, concurrent access
- **Use Case**: Multi-station laboratory, LAN-based

**Mode 3 - Cloud (Online)**:
- **Primary Database**: PostgreSQL 16 with replicas
- **Location**: Cloud infrastructure (AWS, Azure, on-premise)
- **Features**: High availability, read replicas, partitioning
- **Advantages**: National scale, disaster recovery
- **Use Case**: National deployment, multi-site coordination

### 4.2 Module Database Isolation

Each module maintains its own database instance:

**Platform-Core Databases**:
- `platform_core.db` (PostgreSQL) — Core registries
- `knowledge_graph.db` (PostgreSQL + Apache AGE) — Knowledge graph
- `governance.db` (PostgreSQL) — Governance engine

**Module Databases**:
- Each module repository contains its own database
- Database schema defined in module manifest
- No cross-module database queries
- Synchronization via events and APIs

### 4.3 Schema Management

**Migration Strategy**:
- Alembic for PostgreSQL schema migrations
- Version-controlled schema definitions
- Forward and rollback migration scripts
- Automated migration testing

**Schema Versioning**:
- Semantic versioning for schema changes
- Backward compatibility requirements
- Deprecation policy for schema elements
- Migration documentation required

### 4.4 Graph Storage Strategy

**Knowledge Graph**:
- Apache AGE extension for PostgreSQL
- In-memory graph with adjacency lists for performance
- Temporal snapshots for historical evolution
- O(1) node lookups, O(E) traversal

**Graph Schema**:
- 22 node types (Repository, Service, API, Event, Device, etc.)
- 20 relationship types (DEPENDS_ON, PUBLISHES, CONSUMES, etc.)
- Property graph model for metadata
- Temporal tracking for all changes

### 4.5 Data Synchronization

**Offline → Online Sync**:
- Event-driven synchronization when connectivity restored
- Conflict detection via timestamps and version vectors
- Manual conflict resolution for critical data
- Audit trail for all synchronization events

**Multi-Site Sync**:
- Eventual consistency model
- Conflict-free replicated data types (CRDTs) where applicable
- Manual resolution for conflicting updates
- Priority-based conflict resolution rules

### 4.6 Security and Compliance

**Encryption at Rest**:
- SQLite: SQLCipher extension for encryption
- PostgreSQL: Transparent Data Encryption (TDE)
- Key management via government-approved HSMs

**Encryption in Transit**:
- TLS 1.3 for all database connections
- Certificate-based authentication
- VPN for cloud connections

**Audit Logging**:
- All database operations logged
- Immutable audit trail
- 7-year retention for government compliance
- Real-time monitoring for suspicious activity

## 5. Consequences

### 5.1 Positive Consequences

**Operational Benefits**:
- Offline-first capability satisfied by SQLite
- Scalability satisfied by PostgreSQL
- Module independence satisfied by database isolation
- Government security requirements satisfied by encryption and audit

**Development Benefits**:
- SQLAlchemy provides unified ORM for both databases
- Alembic provides consistent migration management
- Pydantic models ensure data validation across databases
- Testing frameworks support both databases

**Compliance Benefits**:
- Constitution Article III (no shared databases) satisfied
- Constitution Article XVII (prohibitions) satisfied
- Data sovereignty supported by deployment mode selection
- Audit trail meets government requirements

### 5.2 Negative Consequences

**Complexity Costs**:
- Two database technologies increase operational overhead
- Synchronization logic adds development complexity
- Testing matrix doubled (SQLite + PostgreSQL)
- Backup and recovery procedures differ by mode

**Performance Costs**:
- SQLite limitations may bottleneck high-concurrency scenarios
- Synchronization operations consume bandwidth
- Graph queries may require optimization for large datasets
- Migration between modes requires data transformation

**Operational Costs**:
- Team must expertise in both SQLite and PostgreSQL
- Monitoring and alerting differ by database
- Disaster recovery procedures vary by deployment mode
- Government audit preparation requires database-specific documentation

---

## 6. Trade-offs

### 6.1 Simplicity vs. Scalability

**Trade-off**: SQLite provides simplicity but limited scalability. PostgreSQL provides scalability but increased complexity.

**Rationale**: Initial deployment is offline-first in government laboratories. National scale is a future requirement that can be addressed with PostgreSQL.

**Mitigation**: Clear deployment mode documentation. Migration guides for mode transitions. Performance monitoring to identify scaling needs.

### 6.2 Consistency vs. Availability

**Trade-off**: Strong consistency within database, eventual consistency across synchronized databases.

**Rationale**: Healthcare data integrity requires ACID within operations. Cross-site consistency can be eventual for non-critical data.

**Mitigation**: Conflict detection and resolution strategies. Priority-based synchronization. Manual resolution for critical conflicts.

### 6.3 Performance vs. Features

**Trade-off**: SQLite performs well for single-user but lacks advanced PostgreSQL features.

**Rationale**: Offline mode prioritizes simplicity and reliability over advanced features. Advanced features available in laboratory and cloud modes.

**Mitigation**: Feature parity documentation. Graceful degradation when features unavailable. Performance profiling to optimize critical paths.

## 7. Risks

### 7.1 Technical Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| SQLite concurrency bottleneck | Medium | High | WAL mode, connection pooling, read replicas |
| PostgreSQL resource requirements too high | Low | Medium | Configuration optimization, resource monitoring |
| Synchronization conflicts cause data loss | Medium | High | Conflict detection, manual resolution, audit trail |
| Apache AGE performance degradation | Low | Medium | Query optimization, indexing, in-memory caching |

### 7.2 Operational Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| Database corruption in offline mode | Low | High | Regular backups, integrity checks, recovery procedures |
| Migration failures during upgrades | Medium | High | Rollback scripts, testing, blue-green deployment |
| Backup and recovery failures | Low | High | Automated backups, recovery testing, documentation |
| Government audit failures | Low | High | Compliance documentation, audit preparation |

### 7.3 Compliance Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| Data sovereignty violations | Low | High | Data residency controls, encryption, access logging |
| Constitution violations undetected | Low | High | Automated compliance checks, continuous monitoring |
| Security vulnerabilities in database | Medium | High | Security scanning, prompt patching, hardening |
