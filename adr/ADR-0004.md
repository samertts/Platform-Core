# ADR-0004: Communication Protocol

**Document**: Architecture Decision Record
**ID**: ADR-0004
**Date**: 2026-06-25
**Status**: Accepted
**Deciders**: Platform Architect, Core Engineering Team
**Constitution Reference**: Articles II, VI, VII, XVII

---

## 1. Context

The Unified Healthcare Platform consists of independent repositories that must communicate while maintaining module independence (Constitution Article II). The platform must support communication patterns that work across diverse deployment scenarios—from isolated government laboratories to national-scale cloud infrastructure.

**Module Independence Requirements** (Constitution Article II):
- Repositories remain independent
- No shared databases
- Communication through APIs, Events, Shared SDKs, Published Contracts
- No code duplication between repositories

**Event Governance** (Constitution Article VI):
- Every significant business action shall publish an event
- Events are immutable, versioned, and documented
- Platform-Core owns the Event Registry

**API Governance** (Constitution Article VII):
- Every API must be versioned, documented, follow platform standards
- Support backward compatibility
- Expose health endpoints, metrics, structured error responses

**Communication Constraints**:
- Must work offline (no network dependency)
- Must support government-grade security
- Must scale from single-lab to national deployment
- Must integrate diverse technologies (Python, TypeScript, Rust)

---

## 2. Problem

The platform needs communication protocols that satisfy:

**Requirement 1 - Module Independence**: Modules communicate through well-defined contracts, never through shared state or databases.

**Requirement 2 - Offline-First Operation**: Communication must work without network connectivity. In-process communication required for standalone deployments.

**Requirement 3 - Event-Driven Architecture**: All significant business actions must publish events (Constitution Article VI). Events must be reliable, ordered, and durable.

**Requirement 4 - API Standards**: All APIs must follow platform standards for versioning, documentation, and error handling (Constitution Article VII).

**Requirement 5 - Technology Diversity**: Communication must work between Python, TypeScript, Rust, and other language modules.

**Requirement 6 - Performance**: Communication must meet latency targets (<10ms for in-process, <50ms for local network).

**Requirement 7 - Security**: All communication must support encryption and authentication.

**Requirement 8 - Observability**: All communication must be traceable and measurable.

## 3. Alternatives Considered

### Alternative A: REST APIs Only

**Description**: All communication via HTTP REST APIs with JSON payloads.

**Pros**:
- Standardized, widely understood
- Language-agnostic
- Tooling support (OpenAPI, Swagger)
- HTTP security (TLS, OAuth2)
- Browser-compatible

**Cons**:
- Requires network for all communication
- Synchronous only (no event-driven)
- High latency for in-process calls
- No offline capability
- Polling required for real-time updates

**Assessment**: REJECTED — Network dependency violates offline-first requirement.

### Alternative B: gRPC Only

**Description**: All communication via gRPC with Protocol Buffers.

**Pros**:
- High performance
- Strong typing via Protocol Buffers
- Bidirectional streaming
- Language-agnostic
- HTTP/2 multiplexing

**Cons**:
- Requires network for all communication
- Complex setup for simple operations
- Browser support limited
- No offline capability
- Steeper learning curve

**Assessment**: REJECTED — Network dependency and complexity incompatible with requirements.

### Alternative C: Message Queue Only (RabbitMQ/Kafka)

**Description**: All communication via message queue with pub/sub patterns.

**Pros**:
- True event-driven architecture
- Decoupled producers and consumers
- Durable messaging
- Scalable and reliable
- Offline support via local queue

**Cons**:
- Infrastructure requirements (message broker)
- Complexity for simple request/response
- Eventual consistency challenges
- Operational overhead for government deployments
- Overkill for single-laboratory scenarios

**Assessment**: REJECTED — Infrastructure requirements incompatible with offline-first deployment.

### Alternative D: Events (In-Process Pub/Sub), REST APIs, SDK Contracts

**Description**: Multi-protocol communication with in-process events for runtime, REST for network, SDK for shared contracts.

**Pros**:
- In-process events satisfy offline-first requirement
- REST APIs satisfy network communication
- SDK contracts ensure compatibility
- Technology-agnostic via standard protocols
- Flexible deployment modes

**Cons**:
- Multiple protocols increase complexity
- Protocol translation required in some scenarios
- SDK versioning adds operational overhead
- Testing matrix increased

**Assessment**: SELECTED — Best balance of offline capability, network communication, and module independence.

### Alternative E: GraphQL Only

**Description**: All communication via GraphQL with schema-first design.

**Pros**:
- Flexible queries
- Strong typing
- Single endpoint
- Real-time subscriptions
- Browser-compatible

**Cons**:
- Requires network for all communication
- No offline capability
- Complexity for simple operations
- Performance overhead for simple queries
- Caching complexity

**Assessment**: REJECTED — Network dependency violates offline-first requirement.

## 4. Decision

**We will adopt Events (in-process pub/sub), REST APIs, and SDK contracts as the communication protocol stack.**

### 4.1 Communication Protocol Stack

**Layer 1 - In-Process Events (Runtime)**:
- In-process event bus for component communication
- Direct method calls for tightly-coupled operations
- Shared memory for high-performance data access
- No network dependency

**Layer 2 - REST APIs (Network)**:
- HTTP/1.1 and HTTP/2 support
- JSON payloads with schema validation
- OpenAPI 3.0 documentation
- Versioned endpoints (`/api/v1/`, `/api/v2/`)
- Health endpoints (`/health`, `/ready`, `/metrics`)

**Layer 3 - SDK Contracts (Shared)**:
- Language-specific SDKs (Python, TypeScript, Rust)
- Shared type definitions
- Version negotiation
- Backward compatibility requirements

**Layer 4 - Event Bus (Production)**:
- Redis Streams for production event bus
- Durable, ordered, replayable events
- Consumer groups for load balancing
- Dead letter queues for error handling

### 4.2 In-Process Event Bus

**Implementation**:
```python
# Event Bus API
event_bus.publish("repository.registered", {
    "repository_id": "repo-123",
    "name": "LabLink-Core",
    "timestamp": "2026-06-25T10:00:00Z"
})

event_bus.subscribe("repository.registered", handler)
```

**Features**:
- Thread-safe publication and subscription
- Event ordering guarantees within process
- Dead letter queue for failed handlers
- Metrics collection for all events
- Correlation IDs for request tracing

**Use Cases**:
- Component-to-component communication within Platform-Core
- Runtime event processing
- Offline event handling

### 4.3 REST API Standards

**Endpoint Structure**:
```
GET    /api/v1/{resource}           # List resources
GET    /api/v1/{resource}/{id}      # Get single resource
POST   /api/v1/{resource}           # Create resource
PUT    /api/v1/{resource}/{id}      # Update resource
DELETE /api/v1/{resource}/{id}      # Delete resource
```

**Request/Response Format**:
```json
{
    "data": { ... },
    "meta": {
        "version": "1.0",
        "timestamp": "2026-06-25T10:00:00Z",
        "correlation_id": "req-123"
    },
    "pagination": {
        "page": 1,
        "per_page": 20,
        "total": 100
    }
}
```

**Error Response Format**:
```json
{
    "error": {
        "code": "VALIDATION_ERROR",
        "message": "Invalid manifest format",
        "details": { ... }
    },
    "meta": {
        "version": "1.0",
        "timestamp": "2026-06-25T10:00:00Z",
        "correlation_id": "req-123"
    }
}
```

**Authentication**:
- JWT Bearer tokens for API access
- API keys for service-to-service
- OAuth2 for external integrations

### 4.4 SDK Contracts

**Python SDK**:
```python
from platform_core.sdk import PlatformClient

client = PlatformClient(base_url="http://localhost:8080")
repository = client.repositories.get("repo-123")
```

**TypeScript SDK**:
```typescript
import { PlatformClient } from '@platform-core/sdk';

const client = new PlatformClient({ baseUrl: 'http://localhost:8080' });
const repository = await client.repositories.get('repo-123');
```

**Contract Requirements**:
- Versioned SDK releases
- Backward compatibility for 2 major versions
- Shared type definitions across languages
- Automated compatibility testing

### 4.5 Production Event Bus (Redis Streams)

**Event Structure**:
```json
{
    "event_id": "evt-123",
    "event_type": "repository.registered",
    "version": "1.0",
    "timestamp": "2026-06-25T10:00:00Z",
    "correlation_id": "req-123",
    "data": {
        "repository_id": "repo-123",
        "name": "LabLink-Core"
    }
}
```

**Event Types**:
- `repository.registered` — New repository added to ecosystem
- `repository.updated` — Repository metadata changed
- `service.health_changed` — Service health status changed
- `governance.finding_created` — New governance finding
- `governance.certification_changed` — Certification status changed

**Guarantees**:
- At-least-once delivery
- Event ordering within partition
- Durable storage (configurable retention)
- Dead letter queue for failed consumers
- Event replay capability

### 4.6 Offline Synchronization

**Local Queue**:
- Events queued locally when offline
- Persistent storage for offline events
- Automatic replay when connectivity restored
- Conflict detection and resolution

**Synchronization Protocol**:
1. Local events stored in SQLite queue
2. When connectivity restored, events published to Redis Streams
3. Events replayed in order for new subscribers
4. Conflicts detected via timestamp and version vectors
5. Manual resolution for critical conflicts

## 5. Consequences

### 5.1 Positive Consequences

**Operational Benefits**:
- Offline-first communication via in-process events
- Network communication via REST APIs
- Module independence via SDK contracts
- Production scalability via Redis Streams

**Development Benefits**:
- Clear communication patterns for developers
- SDK reduces boilerplate code
- API documentation auto-generated
- Event-driven design enables loose coupling

**Compliance Benefits**:
- Constitution Article II (module independence) satisfied
- Constitution Article VI (event governance) satisfied
- Constitution Article VII (API governance) satisfied
- Constitution Article XVII (prohibitions) satisfied

### 5.2 Negative Consequences

**Complexity Costs**:
- Multiple protocols increase learning curve
- Protocol translation required in some scenarios
- SDK versioning adds operational overhead
- Testing matrix increased (multiple protocols)

**Performance Costs**:
- In-process events introduce serialization overhead
- REST API latency for network calls
- SDK abstraction adds minor overhead
- Event bus adds processing latency

**Operational Costs**:
- Redis infrastructure required for production
- SDK maintenance across multiple languages
- API versioning requires deprecation management
- Event schema evolution requires careful planning

---

## 6. Trade-offs

### 6.1 Simplicity vs. Flexibility

**Trade-off**: Multiple protocols provide flexibility but increase complexity.

**Rationale**: Diverse deployment modes (offline, LAN, cloud) require different communication patterns. Single protocol cannot satisfy all requirements.

**Mitigation**: Clear documentation for each protocol. SDK abstracts complexity for developers. Training programs for team.

### 6.2 Performance vs. Reliability

**Trade-off**: In-process events are fast but limited to single process. Redis Streams are reliable but add network latency.

**Rationale**: Offline mode requires in-process performance. Production mode requires Redis reliability. Both modes supported via protocol selection.

**Mitigation**: Protocol selection based on deployment mode. Performance profiling for critical paths. Fallback mechanisms for failure scenarios.

### 6.3 Consistency vs. Availability

**Trade-off**: REST APIs provide synchronous consistency. Event-driven provides eventual consistency.

**Rationale**: Some operations require immediate consistency (authentication, critical updates). Others can tolerate eventual consistency (notifications, analytics).

**Mitigation**: Clear guidelines for when to use each pattern. Consistency requirements documented per API and event type.

## 7. Risks

### 7.1 Technical Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| In-process event bus bottleneck | Medium | High | Profiling, optimization, external bus fallback |
| REST API performance degradation | Low | Medium | Load testing, caching, optimization |
| SDK version incompatibility | Medium | Medium | Semantic versioning, compatibility testing |
| Redis Streams failure | Low | High | Clustering, persistence, fallback to local queue |

### 7.2 Operational Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| Protocol confusion by developers | Medium | Medium | Clear documentation, training, code examples |
| API versioning mistakes | Medium | High | Automated testing, deprecation policies |
| Event schema evolution issues | Medium | High | Versioning, backward compatibility, migration guides |
| SDK maintenance burden | Medium | Medium | Automated testing, CI/CD, community contributions |

### 7.3 Compliance Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| Constitution violations in communication | Low | High | Automated compliance checks, code reviews |
| API security vulnerabilities | Medium | High | Security scanning, penetration testing |
| Event data leakage | Low | High | Encryption, access controls, audit logging |
